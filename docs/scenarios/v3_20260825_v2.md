# Scénario V2 — capture `v3_test_20260825` (camera_1, vue latérale)

## Objectif

Reproduire exactement la chaîne V1→V2 déjà utilisée pour `video1.mp4` (extraction MediaPipe,
lissage, reconstruction planaire contrainte), appliquée à `camera_1_right_lateral_synced.mov`
(session `v3_test_20260825`), avec les mêmes hypothèses (segments 0.30m/0.25m, filtre 2Hz),
puis pousser jusqu'à OpenSim IK — étape que `video1_v2` lui-même n'avait jamais atteinte.

Configurations : `config/scenarios/v3_20260825_v1.json`, `config/scenarios/v3_20260825_v2.json`.
Sorties : `data/scenarios/essais/v3_20260825_v1/`, `data/scenarios/essais/v3_20260825_v2/`.
`essais/video1_v1/` et `pipeline_principal/` (ancien `video1_v2/`) restent intacts (aucun fichier écrasé).

## Chaîne exécutée

```text
camera_1_right_lateral_synced.mov
   -> extract_motion.py (V1) -> motion_raw.csv -> smooth_motion.py -> motion_smoothed.csv
   -> validate_motion.py : FAIL (CV epaule-coude 10.3%, 0% donnees manquantes)
   -> reconstruct_planar_arm.py (V2, fenetre complete 0-1395, pas de phase distincte identifiee)
   -> motion_constrained.csv : EXPLORATORY_PASS
   -> convert_to_trc.py -> motion_exploratory.trc
   -> create_mujoco_target.py : BLOQUE (Smart App Control, voir plus bas)
   -> src/opensim/run_analysis.py (IK, --allow-failed-quality, modele arm26_scaled.osim reutilise tel quel)
```

## Résultat V1/V2 (comparaison à `video1_v2`)

Détail complet dans la conversation ; résumé :

- Détection MediaPipe : 100% (vs 94.4% pour video1.mp4).
- `validate_motion.py` (V1, la mesure non forcée) : FAIL avec 1 seul échec (CV=10.3%) contre 5
  échecs pour video1.mp4 (CV 33.1%/40.0%, données manquantes 2.6-4.5%).
- Amplitude du geste nettement plus petite : épaule 24.0° (vs 114.2°), coude 42.5° (vs 113.4°) —
  reflète un vrai repassage sur place, cohérent avec les 7 cycles mesurés précédemment.

## OpenSim IK — technique OK, résultat non exploitable

**Bug d'environnement corrigé en cours de route** : `src/opensim/run_analysis.py` doit être lancé
avec `.venv38` (bindings OpenSim réels, installés uniquement dans l'environnement Python 3.8 —
voir `docs/windows_setup.md`), pas `.venv310`. Lancé avec `.venv310`, le script importe `opensim`
sans erreur apparente mais résout en fait vers le dossier local `src/opensim/` (nos propres
scripts, homonyme accidentel) au lieu de la vraie API OpenSim — d'où un `AttributeError` tardif
et trompeur (`module 'opensim' has no attribute 'Logger'`). À corriger si ce script est relancé
ailleurs : toujours `.venv38\Scripts\python.exe`, avec `OPENSIM_HOME` et les repertoires DLL
(`bin`, `sdk\lib`, `sdk\Python\opensim`) ajoutes via `os.add_dll_directory`.

**IK a tourné sans erreur** : 1396 frames en 141ms, `analysis_metadata.json` écrit,
`exploratory_override: true` (attendu, `motion_quality_v2.json` n'est jamais littéralement `PASS`).

**Mais le résultat n'a pas de sens physique, et ne doit pas être utilisé :**

| | Mesuré directement (reconstruction V2) | Obtenu par IK |
|---|---:|---:|
| Amplitude épaule | 24.0° | **7.1°** |
| Amplitude coude | 42.5° | **4.8°** |
| Erreur marqueurs RMS | — | **~0.68 m** (seuil 0.02m) |

Cause identifiée : à la pose de référence, `arm26_scaled.osim` a des distances
épaule-coude/coude-poignet de **0.435m / 0.152m** (mesurées directement sur les marqueurs du
modèle), très différentes des longueurs fixes **0.30m / 0.25m** imposées par la reconstruction V2
— et avec un rapport bras/avant-bras inversé par rapport à l'anatomie réelle (le modèle a un
avant-bras plus court que le bras, alors que la reconstruction V2 suppose l'inverse). Avec un tel
écart d'échelle et de proportions, l'optimiseur IK ne peut pas suivre fidèlement les marqueurs ;
il converge vers une pose de compromis qui minimise l'erreur globale sans refléter le mouvement
réellement mesuré. **Les angles IK ci-dessus sont un artefact de ce décalage, pas une mesure plus
précise que la reconstruction V2** — c'est l'inverse : la reconstruction V2 (moins "scientifique"
en apparence) est ici la source la plus fidèle au mouvement réel filmé.

Cette incompatibilité n'avait jamais été testée avant, car `video1_v2` n'avait jamais été poussé
jusqu'à IK (son dossier `opensim/` était resté vide). C'est donc une découverte nouvelle, valable
aussi pour `video1_v2` si la même IK y était tentée : le modèle `arm26_scaled.osim` existant n'est
probablement pas à l'échelle d'aucun des sujets filmés jusqu'ici. Une vraie étape Scale (jamais
implémentée dans ce dépôt — aucun `ScaleTool` n'existe dans `src/`) serait nécessaire avant qu'IK
sur ces données planaires ait un sens.

## Limite technique non résolue : `create_mujoco_target.py`

Bloqué par Windows **Smart App Control** (`SAC="On"`), qui empêche le chargement de `mujoco.dll`
(`OSError: [WinError 4551] An Application Control policy has blocked this file`). SAC ne peut pas
être désactivé sans réinstallation complète de Windows une fois activé — confirmé non résolu pour
l'instant sur cette machine.

Pistes de résolution, par ordre de préférence :
1. Relancer cette étape spécifique sur une autre machine où SAC est désactivé ou désactivable
   (ou jamais activé).
2. Si une politique d'exemption WDAC/SAC gérée par l'organisation existe, demander la signature
   ou l'ajout de `mujoco.dll` (et de tout `.dll`/`.pyd` du paquet `mujoco`) à la liste
   d'exemption — nécessite les droits d'administration du poste, hors de portée ici.
3. Réinstallation de Windows avec SAC désactivé dès l'installation (dernier recours).

Tant que ce n'est pas résolu, `data/scenarios/essais/v3_20260825_v2/target_arm26_exploratory.mot` et
`target_arm26_mapping.json` ne peuvent pas être générés pour ce scénario (ni pour aucun autre sur
cette machine).
